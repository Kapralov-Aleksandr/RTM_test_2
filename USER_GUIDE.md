# Руководство пользователя (для руководителя проекта)

## Первый запуск

`start.bat` → в браузере откроется приложение. По умолчанию включён **демо-режим** с
наполненным проектом «Личный кабинет абитуриента» (ключ **LC**) — можно сразу всё
пощёлкать. Данные демо-режима живут в браузере; для боевой работы запустите backend
(это делает `start.bat`) и выключите демо-режим в боковой панели — данные пойдут в
локальную базу `data/app.db`.

## Боковая панель

- **Активный проект** — переключение между проектами (мультипроектность); «➕ проект» создаёт новый.
  Ключ Jira нового проекта определяет префикс ID требований (`REQ-PROJ-…`).
- **Табы 1–6** — разделы системы. Серые метки «ит.N» означают, что таб войдёт в итерации N.
- **Интеграции** — URL Jira (`https://jira.tomskasu.ru`) и Confluence, логин/пароль,
  ключ проекта. «💾 Сохранить настройки» пишет их в `data/config.json`. Точки-индикаторы
  показывают состояние подключения.

## Таб 2 · Матрица требований (доступен сейчас)

### Создание
«➕ Добавить требование» → форма. Ключ генерируется сам: `REQ-LC-FUNC-0015`
(проект-тип-номер) — предпросмотр виден прямо в форме. «💾 Сохранить» создаёт запись.

### Статусы актуальности (считаются автоматически)
- 🟢 **Актуально** — требование проверено после последнего изменения;
- ⚠ **Требует проверки** — требование редактировали, актуальность не подтверждена;
- 🔴 **Не создано** — для требования ещё нет фиче-страницы/тест-кейсов.

Строка окрашивается по наихудшему из двух статусов (по ФС и по тестам).
Кнопки ✅ в строке подтверждают актуальность.

### Важно про сохранение
Любое «💾 Сохранить» в форме редактирования обновляет `updated_at` — статусы сбрасываются
в «⚠ Требует проверки». Это не баг, а механика: команда (аналитик → QA → разработка)
должна подтвердить, что фиче-страницы и тест-кейсы синхронизированы с изменением.

### 📜 История
Кнопка «📜» в строке — таймлайн изменений: какое поле, старое значение → новое, когда.

### Фильтры и сортировка
Поиск по ID/названию/описанию; фильтры по **типу** (Бизнес/Функциональное/Нефункциональное),
**релизу** и статусу. Клик по заголовку колонки сортирует (повторный клик — в обратную сторону).

### Импорт из Excel/CSV
«⬆ Импорт» → файл → приложение само подберёт соответствие колонок
(Название, Тип, ТЗ, ЧТЗ, Релиз…) → предпросмотр → «Импортировать». ID генерируются автоматически.
«⬇ Экспорт» выгружает текущую выборку в Excel.

## Таб 1 · Исходное ТЗ

1. Откройте таб и наберите/вставьте текст ТЗ (редактор TipTap: заголовки, списки,
   жирный, ссылки — панель сверху).
2. **Выделите фрагмент мышкой** — над выделением появится кнопка **«📌 Зафиксировать
   как требование»**. Нажмите, уточните тип и название — требование создастся
   (ключ `REQ-…` автоматически), а фрагмент подсветится голубым.
3. **Наведение** на подсветку показывает tooltip с ключом требования; **клик** открывает
   его карточку в Табе 2. «Снять» в плавающем меню убирает фиксацию.
4. «Загрузить файл ТЗ» (PDF/DOCX/TXT) сохраняет файл в `data/attachments/` — он появится
   внизу страницы со ссылкой на скачивание.
5. **«💾 Сохранить»** пишет документ и все связи «текст ↔ требование» (с offset'ами) в БД.

## Таб 3 · ЧТЗ

Наберите в тексте **`@REQ-`** (или `@` + фрагмент названия) — появится autocomplete
требований проекта; выбор (мышкой или Enter, ↑↓ — навигация) вставляет кликабельный
бейдж. Под редактором — список всех связанных требований. «💾 Сохранить» пишет документ
в `chtz_documents`.

## Таб 4 · Фиче-страницы

- **Слева — дерево**: релизы (корень) и фичи внутри. «Добавить релиз» — кнопка сверху,
  «Добавить фичу» — правый клик по релизу. **Перетаскивание** перемещает фичи между
  релизами и меняет порядок; правый клик — переименовать/удалить.
- **Справа — фича**: редактор описания (тоже с @-упоминаниями), ссылки на Jira и
  тест-кейсы, **«➕ Привязать требование»** (модалка с поиском по ID/названию),
  **макеты** — перетащите PNG/JPG в зону загрузки (хранятся в `data/mockups/`,
  отображаются галереей). «💾 Сохранить» создаёт/обновляет страницу и `updated_at`.

## Табы 5 и 6 — в следующих итерациях

В навигации они есть с честным роадмапом механик: дашборд рассинхронизаций
(«требование изменилось → фича/тесты не актуализированы», «✅ Подтвердить актуальность»)
и воронка покрытия (пробелы, сироты, экспорт). Логика для них уже написана на бэкенде
(`services/coverage.py`, `services/change_detection.py`).

## Частые вопросы

**Где лежат данные?** В боевом режиме — `data/app.db` (SQLite) и файлы в `data/mockups/`,
`data/attachments/`, `data/snapshots/`. Папка `data/` создаётся автоматически.

**Как подключиться к настоящим Jira/Confluence?** Заполните URL и креды в боковой панели,
выключите демо-режим, сохраните. Запросы идут через backend с `verify=False`
(самоподписанные сертификаты — не помеха), таймаут 10 с, ответы кэшируются 5 минут.

**Что делать с новыми требованиями, прилетевшими по ходу проекта?** В итерации 1 —
создавайте их в матрице (в примечании укажите источник). Журнал Change Requests с
влиянием на бюджет/сроки и автопревращением в атомарные требования запланирован;
таблица `change_requests` в базе уже есть.
